Linux libceph: Multiple Unsafe Decodes in decode_locker() (CVE-2026-80561)

Linux Kernel libceph Client | net/ceph/cls_lock_client.c | Slab Memory Safety | Vulnerability Write-up

1. Summary

```

CVE-2026-80561 is a collection of unsafe decoding operations in the Linux kernel's libceph client within decode_locker() in net/ceph/cls_lock_client.c.

Three separate operations consumed or skipped data without establishing that the requested bytes remained within the received OSD reply:

  • ceph_decode_copy() copied the fixed-size locker_id_t name field without a preceding bounds check.
  • A raw pointer increment skipped sizeof(struct ceph_timespec) bytes without validating the remaining decode range.
  • A bare ceph_decode_32() decoded a variable length, followed by an uncapped *p += len.

Together, these operations allowed malformed OSD replies to violate the parser's fundamental decode-window invariant.

```

```
The affected parser is reachable when kernel Ceph clients process locker information returned by the lock.get_info class method.
```

3. Unsafe Decode #1: locker_id_t Name

```

The first unsafe operation copied the locker name using:

``` 
ceph_decode_copy(p, &locker->id.name,
                 sizeof(locker->id.name));
```

No independent verification established that the requested bytes remained available.

When ceph_start_decoding() accepts struct_len=0, the cursor can be positioned exactly at end. The subsequent copy then attempts to read sizeof(ceph_entity_name), or nine bytes, beyond the validated boundary.

``` 
struct_len = 0
      |
      v
ceph_start_decoding() succeeds
      |
      v
p == end
      |
      v
ceph_decode_copy(..., 9 bytes)
      |
      X
      |
out-of-bounds read
```

The corrected operation is:

``` 
ceph_decode_copy_safe(p, end, &locker->id.name,
                      sizeof(locker->id.name), out_bad);

4. Unsafe Decode #2: Unchecked Timespec Skip

```

The second vulnerability was an unchecked pointer advance:

``` 
*p += sizeof(struct ceph_timespec); /* skip expiration */
```

The parser advanced over the expiration field without proving that the complete field remained within the receive buffer.

This is significant because the decode cursor itself is security- sensitive state. Moving it beyond end breaks the assumptions on which subsequent decoding operations rely.

The raw pointer arithmetic was replaced with:

``` 
/* skip expiration */
ceph_decode_skip_n(p, end, sizeof(struct ceph_timespec), out_bad);
```

The helper verifies the requested range before advancing the cursor.

```

5. Unsafe Decode #3: Length Decode and Uncapped Skip

```

The third issue consisted of an unchecked four-byte length decode followed by an unchecked skip:

``` 
len = ceph_decode_32(p);
*p += len; /* skip description */
```

If the cursor is already at end, the bare ceph_decode_32() performs a four-byte out-of-bounds read.

The decoded value is then used directly to advance the parser cursor. A maliciously large value such as 0xffffffff can move the cursor far outside the intended decode window.

Both stages are now independently bounded:

``` 
ceph_decode_32_safe(p, end, len, out_bad);

/* skip description */
ceph_decode_skip_n(p, end, len, out_bad);

7. Threat Model & Impact Assessment

```
  • CVE: CVE-2026-80561.
  • Primary Issues: Unsafe fixed-size reads, unchecked cursor advancement, and variable-length skips without boundary validation.
  • Confirmed KASAN Primitive: Four-byte slab out-of-bounds read through the bare ceph_decode_32().
  • Attack Vector: A malicious or compromised OSD sends malformed locker information.
  • Reachable Callers: Kernel Ceph clients issuing lock.get_info, including RBD clients performing exclusive lock operations.
  • Privilege Model: Under the stated attacker model, no further privilege is required beyond the ability to establish or control the relevant OSD session.

The demonstrated KASAN report establishes the four-byte out-of-bounds read. The exact consequences of the additional cursor manipulation depend on parser state and surrounding execution context, so no exploitation capability beyond the demonstrated memory-safety conditions is claimed here.

```

8. Remediation

```

The upstream fix replaces all unsafe reads and pointer advances with bounds-aware decoder helpers.

``` 
diff --git a/net/ceph/cls_lock_client.c b/net/ceph/cls_lock_client.c
index 4e6a6d3e4..79a449897 100644
--- a/net/ceph/cls_lock_client.c
+++ b/net/ceph/cls_lock_client.c
@@ -259,7 +259,8 @@ static int decode_locker(void **p, void *end,
        if (ret)
                return ret;

-       ceph_decode_copy(p, &locker->id.name,
-                        sizeof(locker->id.name));
+       ceph_decode_copy_safe(p, end, &locker->id.name,
+                             sizeof(locker->id.name), out_bad);

@@ -270,19 +271,23 @@ static int decode_locker(void **p, void *end,

-       *p += sizeof(struct ceph_timespec); /* skip expiration */
+       /* skip expiration */
+       ceph_decode_skip_n(p, end, sizeof(struct ceph_timespec), out_bad);

        ret = ceph_decode_entity_addr(p, end, &locker->info.addr);
        if (ret)
                return ret;

-       len = ceph_decode_32(p);
-       *p += len; /* skip description */
+       ceph_decode_32_safe(p, end, len, out_bad);
+       /* skip description */
+       ceph_decode_skip_n(p, end, len, out_bad);

        return 0;
+out_bad:
+       return -EINVAL;
 }
```

The new out_bad path returns -EINVAL, correctly classifying the condition as structurally malformed data.
```

10. Upstream Patch & Timeline

CVE-2026-80561 was assigned to the multiple unsafe decode conditions in decode_locker().

The upstream fix commit is: 

437b6551cfcc235eea1d735a874f9d421f555e17

The vulnerable functionality was introduced by: 

d4ed4a530562 ("libceph: support for lock.lock_info")

The patch was marked for stable-tree consideration through Cc: stable@vger.kernel.org.

Version 2 incorporated Viacheslav Dubeyko's review feedback by moving comments above the ceph_decode_skip_n() calls and renaming the error label from bad to out_bad.

Version 3 split the ceph_decode_copy_safe() call to comply with the kernel's 80-column formatting convention following additional review feedback.

The final patch restores a single security invariant throughout the parser: every read and every cursor advance must remain bounded by the received message's end pointer.

11. Key Takeaway

CVE-2026-80561 demonstrates that safe protocol parsing requires validation of both memory accesses and parser-state transitions. 

Read N bytes:
    verify N bytes remain
    |
    v
perform read

Skip N bytes:
    verify N bytes remain
    |
    v
advance cursor

Decode attacker-controlled length:
    validate length field
    |
    v
validate requested skip
    |
    v
advance cursor

The fix applies these rules consistently using ceph_decode_copy_safe(), ceph_decode_32_safe(), and ceph_decode_skip_n().

This prevents malformed OSD replies from causing the parser to read beyond the validated message boundary or move its cursor outside the decode window.
