Linux libceph: Three Unsafe Decodes in decode_locker()

Linux Kernel libceph Client | net/ceph/cls_lock_client.c | Slab Memory Safety | Vulnerability Write-up

1. Summary

```

Multiple unsafe decoding operations existed in the Linux kernel's libceph client within decode_locker() in net/ceph/cls_lock_client.c. The function contained three separate locations where the parser either consumed bytes or advanced its cursor without first establishing that the requested range remained inside the received OSD reply.

The vulnerable operations consisted of an unchecked ceph_decode_copy(), an unchecked pointer advance over a struct ceph_timespec, and an unchecked ceph_decode_32() followed by an uncapped pointer advance using the decoded length.

The underlying issue is the same parser invariant violation seen in other libceph decode paths: successful completion of ceph_start_decoding() does not guarantee that subsequent fields remain available. In particular, struct_len=0 can be accepted, leaving the decode cursor positioned at end.

```

2. Vulnerability Execution Path

```

The vulnerable function parses locker information returned by the Ceph lock.get_info class method:

``` 
Kernel Ceph client
    |
    v
Ceph OSD receives lock.get_info request
    |
    v
OSD returns encoded locker information
    |
    v
net/ceph/cls_lock_client.c
    |
    v
decode_lockers()
    |
    v
decode_locker()
    |
    +-- ceph_start_decoding()
    |       |
    |       +-- struct_len=0 may be accepted
    |       |
    |       +-- p can equal end
    |
    +-- Unsafe decode #1
    |       ceph_decode_copy()
    |
    +-- Unsafe decode #2
    |       *p += sizeof(struct ceph_timespec)
    |
    +-- Unsafe decode #3
            len = ceph_decode_32(p)
            *p += len
```

Under the stated threat model, a malicious or compromised OSD capable of responding to the relevant Ceph client request can supply malformed encoded data to this parser.

The path can be reached when a kernel client issues the lock.get_info class method, including scenarios such as RBD exclusive lock acquisition.

```

3. Unsafe Decode #1: locker_id_t Name

```

The first issue occurs immediately after decoding the initial locker_id_t structure.

``` 
ceph_decode_copy(p, &locker->id.name,
                 sizeof(locker->id.name));
```

This operation performs a raw fixed-size copy without independently checking that the requested bytes remain between *p and end.

If ceph_start_decoding() accepts a malformed encoded structure with struct_len=0, the decode cursor can be left at:

``` 
*p == end
```

The subsequent ceph_decode_copy() then attempts to read sizeof(ceph_entity_name), which is nine bytes in the affected layout, beyond the validated receive-buffer boundary.

``` 
struct_len = 0
      |
      v
ceph_start_decoding() succeeds
      |
      v
*p == end
      |
      v
ceph_decode_copy(..., 9 bytes)
      |
      X
      |
out-of-bounds read
```

The correct primitive already existed in the decoder API:

``` 
ceph_decode_copy_safe(p, end, ...);
```

The safe variant verifies that the entire requested range is available before performing the copy.

```

4. Unsafe Decode #2: Unchecked Timespec Skip

```

The second issue was not a direct load operation but an unchecked pointer advance:

``` 
*p += sizeof(struct ceph_timespec); /* skip expiration */
```

The parser advances over the encoded expiration field without checking whether the entire struct ceph_timespec actually remains inside the receive buffer.

This is particularly dangerous in a stateful decoder because the validity of later operations depends on the integrity of the parser cursor. Once *p is moved beyond end, later checks no longer necessarily describe the original decode window.

``` 
Valid decode window:

        [ buffer start ..................... end ]

Unchecked advance:

        p ------------------------------------^
                                                 \
                                                  +-- p moved beyond end
```

The problem is therefore not merely skipping a missing field. An unchecked cursor advance can corrupt the parser's boundary invariant and invalidate assumptions made by subsequent decoding operations.

The fix replaces the raw pointer arithmetic with the bounds-aware helper:

``` 
ceph_decode_skip_n(p, end,
                   sizeof(struct ceph_timespec),
                   out_bad);
```

This preserves the intended protocol operation while ensuring that the skip occurs only when the complete timespec field remains within the validated buffer.

```

5. Unsafe Decode #3: Length Decode and Uncapped Skip

```

The third issue is a compound parsing sequence:

``` 
len = ceph_decode_32(p);
*p += len; /* skip description */
```

Neither operation independently enforced the decode boundary.

First, ceph_decode_32(p) reads four bytes without checking that those bytes remain available. If p == end, this is immediately a four-byte out-of-bounds read.

Second, the decoded value is used directly as a pointer increment:

``` 
*p += len;
```

There is no verification that len fits within the remaining decode window. A malformed reply can therefore provide an extremely large length, such as:

``` 
len = 0xffffffff
```

The parser cursor can then be advanced far beyond the original message boundary. This breaks the fundamental invariant that all parser movement must remain within the range represented by [p, end].

The fix validates both operations independently:

``` 
ceph_decode_32_safe(p, end, len, out_bad);

/* skip description */
ceph_decode_skip_n(p, end, len, out_bad);
```

The first helper establishes that the four-byte length field exists. The second establishes that the decoded number of bytes actually remains available before advancing the cursor.

```

6. Source Code Analysis

```

The vulnerable code contained the following three unsafe patterns:

``` 
ceph_decode_copy(p, &locker->id.name,
                 sizeof(locker->id.name));

...

*p += sizeof(struct ceph_timespec); /* skip expiration */

...

len = ceph_decode_32(p);
*p += len; /* skip description */
```

All three operations consume or skip data without establishing that the requested bytes remain within the decode boundary.

The corrected implementation uses the existing safe decoding primitives:

``` 
ceph_decode_copy_safe(p, end, &locker->id.name,
                      sizeof(locker->id.name), out_bad);

...

/* skip expiration */
ceph_decode_skip_n(p, end, sizeof(struct ceph_timespec), out_bad);

...

ceph_decode_32_safe(p, end, len, out_bad);
/* skip description */
ceph_decode_skip_n(p, end, len, out_bad);
```

The restored parser invariant

After the fix, every operation that consumes a fixed or variable number of bytes must first prove that those bytes exist:

``` 
Read N bytes:
    verify N bytes remain
    |
    v
perform read

Skip N bytes:
    verify N bytes remain
    |
    v
advance cursor
```

This prevents both direct out-of-bounds accesses and cursor movement beyond the valid decode window.

```

Anatomy of the confirmed read

The valid allocation occupied the range:

``` 
[ffff888009e31000, ffff888009e31fa0)
```

The decode cursor was positioned exactly at:

``` 
p = end = ffff888009e31fa0
```

The bare ceph_decode_32() then attempted to read four bytes starting at the first address outside the allocation. KASAN reported the access as a slab out-of-bounds read immediately to the right of the 4000-byte object.

8. Why 0xCCCCCCCC Matters

```

The value returned by the out-of-bounds length decode was:

``` 
len = 0xcccccccc
```

In the KASAN test environment, this value corresponds to poisoned redzone memory rather than protocol data supplied within the allocated receive buffer.

Its appearance therefore confirms that the bare decoder consumed memory beyond the intended object boundary.

In the vulnerable source sequence, the decoded value would subsequently be used as a pointer increment:

``` 
*p += len;
```

This makes the missing bounds validation particularly important. The parser does not merely read the invalid value; the value participates directly in subsequent cursor movement.

```

9. Threat Model & Impact Assessment

```
  • Primary Memory-Safety Issues: Unsafe fixed-size reads, unsafe pointer advancement, and a variable-length skip without a boundary check.
  • Confirmed KASAN Primitive: A four-byte slab out-of-bounds read through the bare ceph_decode_32().
  • Additional Source-Level Issues: The nine-byte ceph_decode_copy() and both unchecked pointer advances violate the same decode-boundary invariant.
  • Attack Vector: A malicious or compromised OSD supplies a malformed response for the lock.get_info class method.
  • Reachable Callers: Kernel Ceph clients issuing lock.get_info, including RBD clients using exclusive lock functionality.
  • Privilege Requirement: Under the stated attacker model, no additional local privileges are required once the attacker can provide the relevant OSD response.

The KASAN reproduction directly establishes the four-byte out-of-bounds read at the length field. The remaining unsafe operations are established by source-level analysis of their missing bounds checks and are corrected in the same upstream patch.

The exact consequences beyond the demonstrated memory-safety primitives can depend on parser state, allocator state, subsequent callers, and the surrounding kernel environment. This write-up therefore does not claim exploitation capabilities beyond the behavior established by the supplied reproduction and source analysis.

```

10. Remediation

```

The upstream patch replaces all unsafe operations with existing bounds-aware decoding primitives.

``` 
diff --git a/net/ceph/cls_lock_client.c b/net/ceph/cls_lock_client.c
index 4e6a6d3e4..79a449897 100644
--- a/net/ceph/cls_lock_client.c
+++ b/net/ceph/cls_lock_client.c
@@ -259,7 +259,8 @@ static int decode_locker(void **p, void *end,
        if (ret)
                return ret;

-       ceph_decode_copy(p, &locker->id.name,
-                        sizeof(locker->id.name));
+       ceph_decode_copy_safe(p, end, &locker->id.name,
+                             sizeof(locker->id.name), out_bad);

        s = ceph_extract_encoded_string(p, end, NULL, GFP_NOIO);
        if (IS_ERR(s))
                return PTR_ERR(s);
@@ -270,19 +271,23 @@ static int decode_locker(void **p, void *end,
        if (ret)
                return ret;

-       *p += sizeof(struct ceph_timespec); /* skip expiration */
+       /* skip expiration */
+       ceph_decode_skip_n(p, end, sizeof(struct ceph_timespec), out_bad);

        ret = ceph_decode_entity_addr(p, end, &locker->info.addr);
        if (ret)
                return ret;

-       len = ceph_decode_32(p);
-       *p += len; /* skip description */
+       ceph_decode_32_safe(p, end, len, out_bad);
+       /* skip description */
+       ceph_decode_skip_n(p, end, len, out_bad);

        dout("%s %s%llu cookie %s addr %s\n", __func__,
             ENTITY_NAME(locker->id.name), locker->id.cookie,
             ceph_pr_addr(&locker->info.addr));

+out_bad:
+       return -EINVAL;
 }
```

Each operation now independently establishes that the required range remains available before either reading or advancing the parser cursor.

```

11. Error Handling

```

The patch introduces a dedicated out_bad error label:

``` 
out_bad:
        return -EINVAL;
```

-EINVAL is appropriate because a bounds violation during protocol decoding represents structurally malformed input relative to the decode contract.

This failure is distinct from resource exhaustion. Returning -ENOMEM, for example, would incorrectly describe malformed encoded data as an allocator failure.

```

13. Upstream Patch & Timeline

The patch fixes all three unsafe decode operations in decode_locker() and identifies commit d4ed4a530562 ("libceph: support for lock.lock_info") as the introducing commit.

The patch includes Cc: stable@vger.kernel.org for stable-tree consideration.

Version 2 incorporated review feedback from Viacheslav Dubeyko by moving the explanatory comments above the ceph_decode_skip_n() calls and renaming the error label from bad to out_bad.

Version 3 split the ceph_decode_copy_safe() invocation across lines to comply with the kernel's 80-column formatting convention, following further review feedback.

14. Key Takeaway

The three issues demonstrate that safe protocol parsing requires more than checking individual data reads. The parser cursor itself is security-sensitive state. 

Unsafe parser operations:

    Read N bytes without checking N remains
              |
              v
         OOB read

    Advance by N without checking N remains
              |
              v
         Cursor escapes decode window

    Decode attacker-controlled length
    then advance by that length unchecked
              |
              v
         Boundary invariant is lost

A robust decoder must enforce the same rule for both operations: 

Before reading N bytes:
    verify N bytes remain

Before skipping N bytes:
    verify N bytes remain

The upstream fix applies this invariant consistently through ceph_decode_copy_safe(), ceph_decode_32_safe(), and ceph_decode_skip_n().

That prevents malformed OSD replies from moving the decode cursor outside its validated window or causing subsequent operations to consume memory beyond the received buffer.
