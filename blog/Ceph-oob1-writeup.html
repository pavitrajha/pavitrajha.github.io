Linux libceph: Two Unsafe Bare Decodes in decode_lockers() (CVE-2026-68082)

Linux Kernel libceph Client | net/ceph/cls_lock_client.c | Slab Memory Safety | Vulnerability Write-up

1. Summary

A slab out-of-bounds read vulnerability exists in the Linux kernel's libceph client within decode_lockers() in cls_lock_client.c. Two bare decode operations in this function have no preceding bounds check, letting a malicious or compromised Ceph OSD walk the client past the validated end of its receive buffer.

The root cause is a permissive ceph_start_decoding() call. It accepts struct_len=0 as valid, because the internal ceph_decode_need(p, end, 0, bad) check always passes for a zero-length requirement. This leaves p == end, and the two bare decodes that follow read past that boundary without ever checking it.

2. Vulnerability Execution Path

The function is reached whenever a kernel client issues the lock.get_info Ceph class method, most commonly during RBD exclusive lock acquisition: 

net/ceph/osd_client.c
  - Kernel client sends lock.get_info class method call to an OSD as part of
    RBD exclusive lock acquisition or general Ceph lock introspection.
      |
      v
net/ceph/cls_lock_client.c : ceph_cls_lock_info()
  - Receives the OSD reply buffer and hands it to decode_lockers() for parsing.
      |
      v
net/ceph/cls_lock_client.c : decode_lockers()
  - Calls ceph_start_decoding() to validate the initial struct header.
  - struct_len=0 is accepted as valid, so p == end on return.
      |
      v
  - Bare ceph_decode_32(p) reads num_lockers with no bounds check. (Bug 1)
  - decode_locker() loop runs num_lockers times.
  - Bare ceph_decode_8(p) reads the lock type with no bounds check. (Bug 2)

Any kernel client with an established OSD session can reach this path. No additional privilege beyond normal Ceph client-to-OSD trust is required, which means a compromised OSD in a multi-tenant deployment is a sufficient attacker.

3. Vulnerability Description & Mechanics

Bug 1: unchecked num_lockers read. After ceph_start_decoding() returns success with p == end, the very next operation is a bare ceph_decode_32(p): 

*num_lockers = ceph_decode_32(p);

This reads 4 bytes past the validated buffer boundary. The garbage value read from beyond the buffer is passed directly into kzalloc_objs() as the locker allocation count, meaning attacker-influenced heap contents drive an allocation size decision. The sibling function decode_watchers() in osd_client.c already used the safe variant after its own ceph_start_decoding() call; decode_lockers() was the only remaining bare site.

Bug 2: unchecked lock type read. After the decode_locker() loop runs, a second bare decode reads the lock type: 

*type = ceph_decode_8(p);

If an OSD crafts num_lockers so the loop advances p exactly to end, this read also crosses the boundary by one byte. The out-of-bounds byte is written into *type and used by callers as a lock type discriminator, so this bug combines an OOB read with direct influence over downstream lock semantics.

4. Source Code Analysis

Relevant fragment of decode_lockers() prior to the fix: 

if (ret)
        return ret;

*num_lockers = ceph_decode_32(p);                 /* SINK 1: bare, no bounds check */
*lockers = kzalloc_objs(**lockers, *num_lockers, GFP_NOIO);
if (!*lockers)
        return -ENOMEM;

for (i = 0; i < *num_lockers; i++) {
        ret = decode_locker(p, end, *lockers + i);
        if (ret)
                goto err_free_lockers;
}

*type = ceph_decode_8(p);                         /* SINK 2: bare, no bounds check */
s = ceph_extract_encoded_string(p, end, NULL, GFP_NOIO);

Fix applied (v3, incorporating review feedback from Viacheslav Dubeyko and a smatch catch from Dan Carpenter on a stale ret value): 

if (ret)
        return ret;

ceph_decode_32_safe(p, end, *num_lockers, err_inval);
*lockers = kzalloc_objs(**lockers, *num_lockers, GFP_NOIO);
if (!*lockers)
        return -ENOMEM;

for (i = 0; i < *num_lockers; i++) {
        ret = decode_locker(p, end, *lockers + i);
        if (ret)
                goto err_free_lockers;
}

ret = -EINVAL;
ceph_decode_8_safe(p, end, *type, err_free_lockers);
s = ceph_extract_encoded_string(p, end, NULL, GFP_NOIO);
if (IS_ERR(s)) {
        ret = PTR_ERR(s);
        goto err_free_lockers;
}
*tag = s;
return 0;

err_inval:
        return -EINVAL;
err_free_lockers:
        ceph_free_lockers(*lockers, *num_lockers);
        return ret;

Why the goto targets differ

err_inval is a new label used for the pre-allocation failure path, where *lockers does not exist yet and must not be passed to ceph_free_lockers(). err_free_lockers is the existing label, used once *lockers has been allocated and needs to be released. ret is explicitly set to -EINVAL immediately before ceph_decode_8_safe(); without that assignment, a bounds violation on that decode would fall through to err_free_lockers carrying a stale ret of 0 from the preceding successful loop, silently swallowing the error.

Anatomy of the read

The buggy address sits 5998 bytes into a 6000-byte kmalloc-8k allocation, exactly at the point where the validated struct ended and the bare 4-byte decode ran off the end of it. The resulting num_lockers value, 0xccccaaaa, is uninitialized redzone content rather than anything the OSD legitimately sent, and it is fed straight into the allocation-size calculation for the lockers array. Bug 2 shares the identical precondition (a struct that decodes with p left exactly at end), just one byte instead of four, and was confirmed by source analysis and a separate PoC path rather than a second full KASAN capture in this log.

6. Threat Modeling & Impact Assessment

  • Primary Primitive: Slab out-of-bounds read of up to 4 bytes (bug 1) feeding an allocation-size decision, plus a 1-byte OOB read (bug 2) that leaks adjacent slab content into a value callers trust as a lock type discriminator.
  • Secondary Primitive: Attacker-influenced allocation sizing. Since num_lockers comes from unvalidated memory, a crafted or unlucky heap layout can push the allocation request into pathological ranges, affecting downstream allocator behavior.
  • Attack Vector: A malicious or compromised OSD in a multi-tenant Ceph deployment sends a malformed reply to the lock.get_info class method. Any kernel client issuing that call, including RBD clients performing exclusive lock acquisition, is reachable. No privilege beyond an established OSD session is required.
  • CVSS: 9.8 Critical (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H) per the kernel.org CNA assessment.

7. Remediation

The fix replaces both bare decode operations with their bounds-checked _safe variants and adds a dedicated error path for the pre-allocation failure case. 

diff --git a/net/ceph/cls_lock_client.c b/net/ceph/cls_lock_client.c
index c6956f1df..4e6a6d3e4 100644
--- a/net/ceph/cls_lock_client.c
+++ b/net/ceph/cls_lock_client.c
@@ -299,7 +299,7 @@ static int decode_lockers(void **p, void *end, u8 *type, char **tag,
        if (ret)
                return ret;

-       *num_lockers = ceph_decode_32(p);
+       ceph_decode_32_safe(p, end, *num_lockers, err_inval);
        *lockers = kzalloc_objs(**lockers, *num_lockers, GFP_NOIO);
        if (!*lockers)
                return -ENOMEM;
@@ -310,7 +310,8 @@ static int decode_lockers(void **p, void *end, u8 *type, char **tag,
                        goto err_free_lockers;
        }

-       *type = ceph_decode_8(p);
+       ret = -EINVAL;
+       ceph_decode_8_safe(p, end, *type, err_free_lockers);
        s = ceph_extract_encoded_string(p, end, NULL, GFP_NOIO);
        if (IS_ERR(s)) {
                ret = PTR_ERR(s);
@@ -320,6 +321,8 @@ static int decode_lockers(void **p, void *end, u8 *type, char **tag,
        *tag = s;
        return 0;

+err_inval:
+       return -EINVAL;
 err_free_lockers:
        ceph_free_lockers(*lockers, *num_lockers);
        return ret;

-EINVAL is used for both failure paths because the received data is structurally malformed, not a resource exhaustion condition; using -ENOMEM instead would misrepresent the failure class to callers and to stable backporters triaging the error path.

8. Affected Configurations

  • Vulnerable Component: Linux kernel libceph client, net/ceph/cls_lock_client.c.
  • Reachable Callers: Any kernel consumer invoking the lock.get_info Ceph class method, including RBD kernel clients performing exclusive lock acquisition.
  • Configuration Requirements: Kernel built with Ceph client support, connected to a Ceph cluster where an untrusted or compromised OSD may respond.

Upstream Patch & Timeline

Reported upstream to the Ceph client maintainers via the Linux Kernel Mailing List. The patch went through three revisions, with v3 combining both bugs into a single patch per review feedback from Viacheslav Dubeyko and addressing a stale error-code issue flagged by smatch.
