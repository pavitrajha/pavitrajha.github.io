Introduction

Welcome

Android's Binder driver sits at the center of almost every meaningful interaction between applications and the operating system. Every system service request, every permission-protected operation, and nearly every cross-process interaction ultimately relies on Binder. Because of that, Binder is simultaneously one of Android's most important architectural components and one of its most valuable security research targets.

This booklet accompanies the webinar "Android's Nervous System: Binder IPC Internals and Fuzzing for New Vulnerabilities". Rather than presenting Binder as a collection of kernel structures, the goal is to build an intuitive understanding of how the subsystem actually operates, how security researchers reason about its implementation, and how that understanding naturally leads into effective fuzzing.

The material assumes basic familiarity with Linux, C or C++, and general operating system concepts, but no prior experience with Android internals is required. Whether your objective is vulnerability research, kernel development, or simply understanding one of Android's most critical subsystems, this booklet is intended to serve as both a learning resource and a future reference.

This booklet is designed to be read sequentially. Each chapter builds upon the previous one, progressing from Binder architecture, to transaction processing, to attack surface analysis, and finally to practical Binder fuzzing demonstrations.

Section 01 / 0:00 to 0:10

Why Binder Matters

No internals yet. The only goal for the first ten minutes is to answer the question an audience member is silently asking: why spend two hours on this one piece of code when there are hundreds of kernel drivers?

The fundamental argument

Every networked system has chokepoints - narrow places where all traffic passes through regardless of where it came from or where it's going. The security value of a chokepoint is not just that you can monitor it. It's that a bug there affects everything that crosses it.

Binder is Android's chokepoint. It is not one service or one app - it is the mechanism that makes services and apps possible in the first place. The Android design decision to use a custom kernel IPC driver rather than standard POSIX sockets or System V IPC was intentional: they needed something that could enforce process identity, carry object references across process boundaries, and do it with a single copy rather than the double-copy that standard IPC requires. The result is binder.c - a 6,642 line kernel driver that has been running on every Android device since 2008.

Six actions, one driver

These are not edge cases. These are things a user does within the first thirty seconds of picking up their phone.

What "open the camera" actually calls
Camera App - calls CameraManager.openCamera()
| (Java API call, eventually reaches native)
CameraService - system_server process, different UID
| (cross-process call required here)
Binder transaction - driver copies the request, translates object refs
| (kernel space - this is binder.c)
CameraService receives BR_TRANSACTION, dispatches to handler
| (reply takes the same path back)
App receives camera device handle - also a Binder object
  • Opening the camera asks CameraService for device access - cross-process Binder call
  • Installing an APK routes through PackageManagerService - Binder call, carries file descriptors
  • Requesting GPS location goes through LocationManagerService - Binder, with callback objects
  • Launching any Activity round-trips through ActivityManagerService - two Binder transactions minimum
  • Unlocking the screen talks to the keystore and LockSettingsService - Binder, security-critical path
  • Any permission check, any service binding, any broadcast - all Binder transactions

In every one of those cases, the app process and the service process share no memory. They cannot call each other's functions directly. The kernel mediates every single exchange - and "the kernel" in this context means binder_transaction() at line 2905 of binder.c, which we are going to read together today.

What the attack surface looks like from a researcher's perspective

The exploitability argument is simple. A bug in a camera driver affects devices with that camera. A bug in a GPU driver affects devices with that GPU. A bug in binder.c affects every Android device running that kernel. The attack surface is reachable from a sandboxed app - no hardware access required, no special permissions, just an open() on /dev/binder and an ioctl(). And the code that handles that ioctl is parsing data that entirely came from the calling process, which means it came from an attacker if the calling process is malicious.

If almost everything on the device crosses this one driver, what happens when the driver breaks?

Section 02a / 0:10 to 0:22

Locking Model and the Four Structs

The binder.c file opens with a locking comment before a single line of logic. That comment is not documentation - it is a threat model. It tells you exactly what the driver considers important enough to protect with a spinlock, which is a direct map to where races and use-after-free bugs will concentrate.

The locking comment - verbatim from the file

drivers/android/binder.c
Lines 8–38
/*
 * Locking overview
 *
 * There are 3 main spinlocks which must be acquired in the
 * order shown:
 *
 * 1) proc->outer_lock : protects binder_ref
 *    binder_proc_lock() and binder_proc_unlock() are
 *    used to acq/rel.
 * 2) node->lock : protects most fields of binder_node.
 *    binder_node_lock() and binder_node_unlock() are
 *    used to acq/rel
 * 3) proc->inner_lock : protects the thread and node lists
 *    (proc->threads, proc->waiting_threads, proc->nodes)
 *    and all todo lists associated with the binder_proc
 *    (proc->todo, thread->todo, proc->delivered_death and
 *    node->async_todo), as well as thread->transaction_stack
 *    binder_inner_proc_lock() and binder_inner_proc_unlock()
 *    are used to acq/rel
 *
 * Any lock under procA must never be nested under any lock at the same
 * level or below on procB.
 *
 * Functions that require a lock held on entry indicate which lock
 * in the suffix of the function name:
 *
 * foo_olocked() : requires node->outer_lock
 * foo_nlocked() : requires node->lock
 * foo_ilocked() : requires proc->inner_lock
 * foo_oilocked(): requires proc->outer_lock and proc->inner_lock
 * foo_nilocked(): requires node->lock and proc->inner_lock
 * ...
 */
Read the function suffix convention as a machine-checkable contract. Every time you see binder_foo_ilocked() called in the codebase, you know inner_lock must be held at that callsite. If you ever find an _ilocked function being called without the lock - that is a bug. This convention is how you audit the driver without needing to trace every spinlock acquisition manually.

What the three-lock order means for bug finding

The requirement that locks must be acquired in order (outer -> node -> inner) prevents classic deadlocks where thread A holds lock 1 waiting for lock 2 while thread B holds lock 2 waiting for lock 1. But it also means any code path that acquires these locks in the wrong order is introducing a deadlock risk. And any code path that drops a lock mid-operation to call into sleeping code (like memory allocation) and then reacquires it is creating a window where another thread can modify the protected data.

The teardown path in binder_deferred_release, which we will look at in Section 03b, drops and reacquires inner_lock on every iteration of the nodes loop. That pattern is structurally correct but only if every caller that accesses nodes concurrently respects the tmpref increment discipline. If any caller forgets to increment tmpref before dropping the lock, the node can be freed under it. That is the entire lifetime model in one sentence.

foo_olocked()
-- requires proc->outer_lock (lock #1)
foo_nlocked()
-- requires node->lock (lock #2)
foo_ilocked()
-- requires proc->inner_lock (lock #3)
foo_oilocked()
-- requires outer_lock AND inner_lock
foo_nilocked()
-- requires node->lock AND inner_lock

How binder_init_node_ilocked actually inserts a node

Rather than just describing what binder_node contains, here is the actual insertion code - which shows the rb-tree walk and the tmpref initialization that the rest of the lifetime model depends on:

drivers/android/binder.c
Lines 790–845
static struct binder_node *binder_init_node_ilocked(
            struct binder_proc *proc,
            struct binder_node *new_node,
            struct flat_binder_object *fp)
{
    struct rb_node **p = &proc->nodes.rb_node;
    struct rb_node *parent = NULL;
    struct binder_node *node;
    binder_uintptr_t ptr = fp ? fp->binder : 0;
    binder_uintptr_t cookie = fp ? fp->cookie : 0;
    __u32 flags = fp ? fp->flags : 0;

    assert_spin_locked(&proc->inner_lock);  /* enforces naming convention */

    while (*p) {
        parent = *p;
        node = rb_entry(parent, struct binder_node, rb_node);
        if (ptr < node->ptr)
            p = &(*p)->rb_left;
        else if (ptr > node->ptr)
            p = &(*p)->rb_right;
        else {
            /*
             * A matching node is already in the rb tree.
             * Abandon the init and return it.
             */
            binder_inc_node_tmpref_ilocked(node);
            return node;
        }
    }
    node = new_node;
    binder_stats_created(BINDER_STAT_NODE);
    node->tmp_refs++;              /* caller holds this ref */
    rb_link_node(&node->rb_node, parent, p);
    rb_insert_color(&node->rb_node, &proc->nodes);
    node->debug_id = atomic_inc_return(&binder_last_id);
    node->proc = proc;
    node->ptr = ptr;               /* userspace pointer = rb-tree key */
    node->cookie = cookie;         /* returned on BR_TRANSACTION */
    node->accept_fds = !!(flags & FLAT_BINDER_FLAG_ACCEPTS_FDS);
    spin_lock_init(&node->lock);
    INIT_LIST_HEAD(&node->async_todo);
    return node;
}
Three things to note: (1) the assert_spin_locked at the top - this is the _ilocked naming convention enforced at runtime in debug builds. (2) tmp_refs is set to 1 before the node is inserted - the caller holds the initial reference. (3) the node's ptr field is the userspace pointer, keyed directly from the flat_binder_object. This means if two transactions race to create a node with the same ptr, the second one finds the existing node and increments its tmpref instead of creating a duplicate. The rb-tree walk under inner_lock is what makes this race-safe.

The relationship the rest of the talk depends on

Struct ownership and lifetime dependencies
binder_proc (lives while /dev/binder fd is open)
|-- owns (via proc->nodes rb-tree, protected by inner_lock)
binder_node (lives while proc owns it OR any binder_ref points to it)
|-- referenced by (via node->refs hlist)
binder_ref (in a DIFFERENT proc's refs_by_desc rb-tree)
If binder_proc dies before binder_ref is cleaned up, binder_ref->node is a dangling pointer.
UAF: ref->node accessed after node->proc is NULL and node is freed
The invariant everything else enforces: a binder_node must not be freed while any code path holds a pointer to it that is not backed by a tmpref increment. Every UAF in this driver's history is a violation of this rule - under a race condition, under a missed cleanup, or under a refcount path that two concurrent operations disagree about.

Section 02b / 0:22 to 0:30

binder_ioctl - The Front Door

There is one function every transaction passes through without exception. Not one of several - one. If you are writing a fuzzer that targets the driver layer, you open /dev/binder and you call ioctl() into this function. Everything else in the driver is downstream of this single entry point. It is at line 5423 of the source file.

The complete ioctl handler

drivers/android/binder.c
Lines 5423–5530
static long binder_ioctl(struct file *filp,
                         unsigned int cmd,
                         unsigned long arg)
{
    int ret;
    struct binder_proc *proc = filp->private_data;
    struct binder_thread *thread;
    void __user *ubuf = (void __user *)arg;

    trace_binder_ioctl(cmd, arg);

    ret = wait_event_interruptible(binder_user_error_wait,
                                   binder_stop_on_user_error < 2);
    if (ret) goto err_unlocked;

    thread = binder_get_thread(proc);   /* create or find thread struct */
    if (thread == NULL) {
        ret = -ENOMEM;
        goto err;
    }

    switch (cmd) {
    case BINDER_WRITE_READ:
        ret = binder_ioctl_write_read(filp, arg, thread);
        break;

    case BINDER_SET_MAX_THREADS: {
        u32 max_threads;
        if (copy_from_user(&max_threads, ubuf, sizeof(max_threads))) {
            ret = -EINVAL; goto err;
        }
        binder_inner_proc_lock(proc);
        proc->max_threads = max_threads;   /* no upper bound check */
        binder_inner_proc_unlock(proc);
        break;
    }

    case BINDER_SET_CONTEXT_MGR_EXT: {
        struct flat_binder_object fbo;
        if (copy_from_user(&fbo, ubuf, sizeof(fbo))) {
            ret = -EINVAL; goto err;
        }
        ret = binder_ioctl_set_ctx_mgr(filp, &fbo);
        break;
    }

    case BINDER_SET_CONTEXT_MGR:
        ret = binder_ioctl_set_ctx_mgr(filp, NULL);
        break;

    case BINDER_THREAD_EXIT:
        binder_thread_release(proc, thread);
        thread = NULL;
        break;

    case BINDER_VERSION: {
        struct binder_version __user *ver = ubuf;
        if (put_user(BINDER_CURRENT_PROTOCOL_VERSION,
                     &ver->protocol_version)) {
            ret = -EINVAL; goto err;
        }
        break;
    }

    case BINDER_GET_NODE_INFO_FOR_REF: {
        struct binder_node_info_for_ref info;
        if (copy_from_user(&info, ubuf, sizeof(info))) {
            ret = -EFAULT; goto err;
        }
        ret = binder_ioctl_get_node_info_for_ref(proc, &info);
        if (ret < 0) goto err;
        if (copy_to_user(ubuf, &info, sizeof(info))) {
            ret = -EFAULT; goto err;
        }
        break;
    }

    case BINDER_FREEZE: {
        /* ... copies binder_freeze_info from userspace,
               locks binder_procs_lock, walks proc list ... */
        break;
    }
    }
    /* cleanup and return ... */
}
The first thing binder_ioctl does is pull the binder_proc off filp->private_data (set during binder_open()) and then call binder_get_thread() to find or create a binder_thread struct for the calling thread. From this point, every operation has both a proc and a thread in scope - and both are pointers into the struct hierarchy from Section 02a. Note BINDER_SET_MAX_THREADS: it copies a u32 from userspace and writes it directly into proc->max_threads with no upper bound enforcement. A process can set this to 0xFFFFFFFF. Whether that is exploitable depends on how max_threads is consumed downstream, but it is the kind of unchecked input that is worth examining.

Why BINDER_WRITE_READ is where almost everything real goes

BINDER_WRITE_READ is the ioctl command that carries actual transactions. It routes to binder_ioctl_write_read(), which reads a struct binder_write_read from userspace, then dispatches the write side to binder_thread_write() at line 3926 and the read side to binder_thread_read() at line 4495. binder_thread_write() is where BC_TRANSACTION and BC_REPLY commands land, which call into binder_transaction() at line 2905 - the function that does the actual parsing and copying.

BINDER_WRITE_READ dispatch chain
binder_ioctl() -- line 5423
| cmd == BINDER_WRITE_READ
binder_ioctl_write_read() -- copies struct binder_write_read from userspace
| write_size > 0: dispatch write buffer first
binder_thread_write() -- line 3926
| cmd == BC_TRANSACTION or BC_REPLY
binder_transaction() -- line 2905 (the big one)
| after write: if read_size > 0
binder_thread_read() -- line 4495 (target thread wakes here)

Other ioctl commands as secondary surfaces

Command What it reads from userspace Where it goes
BINDER_SET_MAX_THREADS u32 max_threads Written directly to proc->max_threads, no upper bound check in this version
BINDER_SET_CONTEXT_MGR_EXT struct flat_binder_object binder_ioctl_set_ctx_mgr() - registers this proc as the context manager (servicemanager)
BINDER_GET_NODE_INFO_FOR_REF struct binder_node_info_for_ref Looks up a node by handle, returns debug info - reads from the ref rb-tree under outer_lock

For a fuzzer at the ioctl layer: BINDER_WRITE_READ is the primary target because it carries arbitrary transaction data into binder_transaction(). The others are worth covering in your mutation corpus because BINDER_FREEZE, for example, takes a pid from userspace and walks the global proc list - racing BINDER_FREEZE with a concurrent close() of the same proc's fd is the kind of concurrent pattern that has historically produced bugs.
Now we go inside binder_transaction() - the function that actually resolves the target, allocates a buffer, and copies the transaction data. This is where most of the interesting parsing happens.
Section 02c / 0:30 to 0:40

Walking a Transaction

binder_transaction() at line 2905 is the longest and most complex function in the driver. It does target resolution, buffer allocation, the object offset loop, and object translation - all in sequence, with error paths that have to correctly unwind everything the happy path did. This page walks the first half: how the target is found.

What the function receives and sets up

                              struct binder_thread *thread,
                              struct binder_transaction_data *tr,
                              int reply,
                              binder_size_t extra_buffers_size)
{

    struct binder_proc *target_proc = NULL;
    struct binder_thread *target_thread = NULL;
    struct binder_node *target_node = NULL;
    struct binder_transaction *in_reply_to = NULL;
    uint32_t return_error = 0;
    binder_size_t last_fixup_obj_off = 0;

    /* ... logging setup ... */

    t = kzalloc_obj(*t);            /* allocate the transaction struct */
    if (!t) { return_error = BR_FAILED_REPLY; goto err_alloc_t_failed; }
    INIT_LIST_HEAD(&t->fd_fixups);  /* deferred FD fixup list -- important later */
    spin_lock_init(&t->lock);

    t->from_pid = proc->pid;
    t->from_tid = thread->pid;
    t->sender_euid = current_euid();
    t->code = tr->code;
    t->flags = tr->flags;
    t->is_async = !reply && (tr->flags & TF_ONE_WAY);

The transaction struct copies metadata from the binder_transaction_data that came from userspace: the target handle, the code (like the RPC method number), the flags, and the calling thread's euid. Notice that t->sender_euid = current_euid() - this is the security-relevant identity that service implementations use to enforce permissions. It comes from the kernel, not from the userspace process, which is one reason Binder is trusted for permission enforcement where socket-based IPC is not.

Target resolution - how a handle number becomes a node pointer

If this is not a reply (reply == 0), the driver has to resolve tr->target.handle - the integer handle number the calling process is using - into a binder_proc and binder_node it can actually deliver the transaction to. This involves the binder_ref lookup under outer_lock.

Object Translation and the FD Lifetime Model

The object offset loop dispatches to a family of binder_translate_* functions. Each one takes an object from the sender's parcel and transforms it so it is valid in the target process's address space. For file descriptors, this cannot be done immediately - which produces a two-phase pattern that has historically been the home of file descriptor lifetime bugs.

Why FD translation has to be deferred

When a process sends a file descriptor through Binder, the target process needs to receive a file descriptor number that is valid in its own fd table - not the sender's. Duplicating an fd into another process's fd table using get_unused_fd_flags() and fd_install() has to happen from a thread running in that process's context, because fd tables are per-process kernel structures. binder_translate_fd() runs in the sender's context, so it cannot do this directly.

Instead, it creates a fixup record, stores the file struct reference in it, and queues the record on t->fd_fixups. The actual fd allocation happens later, when the target thread consumes the transaction via binder_thread_read(). This is the deferred fixup pattern.

The lifetime window this creates: after binder_translate_fd() succeeds, t->fd_fixups contains a fixup record holding a reference to the file struct. That reference is not released until either (a) the target thread processes the fixup and installs the fd, or (b) the transaction is torn down via binder_free_txn_fixups(), which calls fput() on every file in the list. If binder_free_txn_fixups() is not called on all error paths that abort the transaction, the file struct leaks. If it is called twice, that is a double-fput - use-after-free on the file struct's reference count.

The Evolution of Binder Security

Binder was not designed to be secure in one pass. What you see in binder.c today is the product of more than twelve years of incremental engineering responses to real failures in real systems. Understanding how it evolved is more instructive than cataloguing what it got wrong.

Why Binder keeps changing

Most kernel subsystems stabilize. Their interfaces settle, their invariants are established, and changes become infrequent. Binder has not done this. New fixes continue shipping in every kernel stable series because the problem space Binder operates in keeps expanding.

The original Binder driver was designed for a relatively simple Android ecosystem: a modest number of system services, synchronous transactions, and a straightforward lifetime model where each object's owner was unambiguous. Every assumption that seemed safe in 2008 has since been stress-tested against a fleet of billions of devices, aggressive memory pressure, multithreaded app runtimes, a Linux MM subsystem that itself kept evolving, and a security research community that reads kernel source code.

The result is a driver that has been modified in fundamental ways more than once. Lock granularity changed. The VMA pointer storage strategy was added, reverted, and redesigned. Reference counting gained explicit temporary references. The freeze notification subsystem introduced an entirely new category of asynchronous lifetime relationships. Offset validation that should have existed from the beginning was added incrementally as the consequences of its absence became concrete.

None of these changes happened because the original engineers were careless. They happened because the system grew in ways that outpaced the assumptions its lifetime model was built on.

Three forces that drove each phase

Looking across the full history, three forces consistently triggered changes to the driver.

The first is Linux MM evolution. Binder has never existed in isolation from the broader kernel. When the MM subsystem changed how mmap_lock is held during munmap() in commit dd2283f2605e, Binder's assumption that mmap_read_lock() was sufficient to protect alloc->vma became incorrect overnight. The driver had to respond to a change it did not control.

The second is concurrency at scale. The lock model described in the header comment - outer_lock, node->lock, inner_lock in strict order - was sound from the start. But as Android added asynchronous work, workqueues, freeze notifications, and deferred cleanup, new code paths appeared that interleaved with that lock model in ways the original design did not anticipate. Each new asynchronous feature introduced new lifetime relationships that the existing reference discipline had to be extended to cover.

The third is input validation gaps surfacing late. Several recent fixes address checks that arguably should have existed from the beginning - offset alignment validation, raw data bounds checking before the offsets array is overwritten - but whose absence only became consequential when more adversarial inputs reached the parsing code. Validation requirements became visible through the consequences of their absence.

Binder did not become secure in one redesign. It evolved through many small engineering corrections, each one closing a gap that the previous design had not anticipated.

Major Turning Points in Binder Security

Four eras defined how Binder's security model changed. Each era produced a cluster of related fixes that share a common root cause and a common engineering response. Read chronologically, they show a subsystem progressively strengthening its ownership guarantees under increasing complexity.

Era I - 2019: Explicit lifetime management becomes mandatory

Before 2019, Binder's reference model relied heavily on implicit assumptions: that a binder_thread would not be freed while an ioctl was in progress on it, that a binder_proc would outlive the transactions it was serving, that the cleanup order during process exit was deterministic enough that no concurrent path could observe a half-freed object. These assumptions held well enough for a long time.

CVE-2019-2215 demonstrated concretely that they did not hold under adversarial scheduling. The bug was a use-after-free in binder_poll(): a binder_thread's wait queue entry could be accessed after the thread was freed because nothing prevented the thread's destruction from racing with a concurrent epoll operation. The root cause was not a missing check or a wrong value - it was the absence of any mechanism to extend a thread's lifetime beyond its nominal scope.

The engineering response was not just to fix that one race. It was to establish a general principle: any code path that loads a pointer to a binder object and then drops the lock protecting it must explicitly increment a temporary reference before doing so. This is the tmp_refs discipline that Section 2 described, and it was significantly hardened across the driver following this period.

Engineering Lesson - 2019: Implicit lifetime assumptions break under concurrency. Once a subsystem is used from multiple threads and processes simultaneously, the only safe model is one where every object's lifetime is explicitly extended by the code that needs it. The binder_thread, binder_node, and binder_proc structures all gained or strengthened tmp_ref mechanisms as a direct consequence of this period.

Era II - 2023: VMA and mm lifetime force a fundamental rethink

Binder's memory allocator in binder_alloc.c maintains a pointer to the process's VMA (alloc->vma) and a pointer to its mm_struct (alloc->vma_vm_mm). This design allowed the allocator to insert pages into a process's address space during transactions without going through a syscall. The design worked until the Linux MM subsystem changed the semantics of mmap_sem during munmap().

Commit dd2283f2605e ("mm: mmap: zap pages with read mmap_sem in munmap") caused munmap() to downgrade the mmap write lock to a read lock after detaching the VMA from the rbtree. This meant that the VMA could be in the process of being torn down and freed while another thread held only the read lock - which was exactly what binder_update_page_range() was doing. Three separate fixes addressed three separate code paths that shared this assumption.

CVE-2023-54157 - binder_update_page_range(): mmap_read_lock was no longer sufficient

The immediate fix for the VMA race in binder_update_page_range() was to revert from mmap_read_lock() back to mmap_write_lock(). This was the conservative, correct fix: the write lock guarantees that no concurrent munmap() can complete while binder is accessing the VMA.

Recurring Engineering Principles

Reading Binder's patch history as a whole, five principles appear again and again - not as rules that were always followed, but as lessons that were learned each time they were violated. Understanding these principles is what lets you read new Binder code and immediately know where to look for gaps.

Principle 1 - Ownership must be explicit

In a subsystem where objects cross process boundaries and outlive the processes that created them, ownership cannot be inferred from context. It must be declared. Binder learned this progressively: first for binder_node (which can outlive its owning proc when other processes still hold refs), then for binder_thread (which must survive an ioctl in progress even if the thread calls BINDER_THREAD_EXIT), then for binder_proc (which must survive cleanup on the workqueue even while concurrent transactions decrement its refcount).

The mechanism Binder uses is tmp_refs - a counter that any code path increments before dropping the protecting lock and decrements when it is done with the object. The naming convention (binder_inc_node_tmpref_ilocked, binder_put_node, binder_proc_dec_tmpref) makes ownership transfers explicit in the function call itself.

binder_inc_node_tmpref_ilocked(node)
-- caller now owns a temporary reference to this node
binder_put_node(node)
-- releases temporary reference, may free node
binder_proc_dec_tmpref(proc)
-- releases temporary reference, may free proc if is_dead and threads empty
binder_thread_dec_tmpref(thread)
-- releases temporary reference to a binder_thread

The 2019 period dramatically extended the scope of this discipline. The 2024 freeze fixes showed it still needs to be applied to every new iteration pattern - binder_add_freeze_work() missed it on first implementation.

Principle 2 - Lifetime extends until all users are done, not until the owner is done

A binder_node is not freed when its owning proc exits. It is freed when its owning proc exits AND no other binder_ref in any other process still points to it. A binder_proc is not freed when its /dev/binder fd is closed. It is freed when that fd is closed AND no in-flight transaction holds a pointer to it AND its tmp_ref reaches zero.

This distinction - between the owner's lifetime and the object's lifetime - is what makes Binder's cleanup code complex. binder_node_release() captures it directly: if the node still has external refs when its proc dies, it is moved to the binder_dead_nodes list rather than freed, and death notifications are queued for every process that holds a ref. The node's memory is not reclaimed until the last ref drops.

| Is node->refs empty AND tmp_refs == 1?

The VMA lifetime bugs from 2023 are a different manifestation of the same principle. Binder's allocator cached alloc->vma because it assumed the VMA's lifetime was tied to the process lifetime. When the MM subsystem changed so that a VMA could be freed while only a read lock was held, that assumption became a UAF. The fix - vma_lookup() instead of cached pointer, or write lock to serialize with munmap() - extends the effective protected lifetime of the VMA to match what the code actually needed.

Principle 3 - Synchronization must cover the entire lifetime window, not just the access

A lock that protects an access does not protect the pointer to the object being accessed. The outer_lock protects proc->refs_by_desc, meaning it serializes insertions and removals from the ref rbtree. But once a binder_ref pointer is loaded from the tree, the outer_lock can be dropped - and at that point, the node the ref points to is protected only by the ref's own existence (via node->refs hlist) and by the tmp_refs discipline.

This is the "lifetime window" problem: there is a gap between loading a pointer (under the lock) and using what the pointer points to (without the lock). Any bug that involves accessing data between those two points requires the code to hold a reference that extends the pointed-to object's lifetime across that gap - not just hold the lock at the moment of access.

The mmput() vs do_exit() race (CVE-2023-52609) is a synchronization lifetime window bug: mmget_not_zero() extended the mm's refcount, but the cleanup work triggered by the final mmput() ran on the wrong thread at the wrong time. Replacing mmput() with mmput_async() moved the cleanup to a context that does not block on the waiting thread's schedule.

Principle 4 - Validation belongs at the boundary, not downstream

Both validation fixes from 2024 share the same structural problem: a check that was performing validation was removed as part of a refactoring, and the replacement code did not include an equivalent explicit check. In both cases, the absence of the check was not immediately obvious because the code "worked" for well-formed inputs - the bug only manifested when an adversarial input was constructed to trigger the specific missing boundary.

The offset alignment check in binder_get_object() (CVE-2024-26926) had been present before commit 7a67a39320df and was noted in the commit message as "likely removed due to redundancy at the time." The bounds check on the raw data copy (CVE-2024-46740) was never present - it was a gap left by the original implementation of binder_transaction()'s object loop that only surfaced when the error path was triggered by a specific combination of object offsets and raw data sizes.

The pattern: validation that is implicit in one version of the code becomes a gap when the code changes. This applies directly to the offset loop in binder_transaction() that Section 2 walked through. Every field in that loop that comes from userspace - hdr->type, object_offset, off_start_offset, off_end_offset, copy_size - is a boundary. Validation at the point where each field is first read prevents downstream code from operating on values it was not designed to handle.

Principle 5 - Cleanup ordering must be complete and symmetric

For every initialization path, there must be a corresponding cleanup path, and every cleanup path must handle every state that the initialization path can produce. This sounds obvious but consistently proves difficult in practice when features are added incrementally.

The freeze notification bugs (CVE-2024-56553, CVE-2024-56554) are both cleanup ordering failures. Adding ref->freeze required updating binder_cleanup_ref_olocked() to dequeue ref->freeze->work, just as it already dequeued ref->death->work. Adding proc->delivered_freeze required updating binder_deferred_release() to call binder_release_work() on that list, just as it already did for proc->delivered_death. Adding BINDER_WORK_CLEAR_FREEZE_NOTIFICATION required updating binder_release_work()'s switch statement to handle the new work type.

Each of these was a separate omission. Each produced a separate CVE. The pattern suggests that the right engineering practice when adding new parallel state (a new work type, a new ref field, a new proc list) is to audit every function that handles the existing parallel state and ask explicitly whether it needs to be updated for the new state as well.

The binder.c you read in Section 2 - the 6,642-line file cited at the top of this booklet - is not the driver that shipped in 2008. It is the result of more than a decade of incremental corrections, each one responding to a concrete failure and each one extending the driver's understanding of what "correct lifetime management" requires.

Modern Binder reflects more than a decade of incremental refinement. Every invariant in the code exists because something once broke without it. Knowing which invariant a given function is enforcing is the difference between reading code and understanding it.

Section 04

Why Fuzz Binder?

Up to this point we have studied Binder from the perspective of the kernel developer and security researcher. We now understand how transactions are created, how objects are translated, how references are managed, and where the driver's most security-sensitive code paths exist. The natural question is therefore: How do we systematically explore all of those code paths? The answer is fuzzing.

What Is Fuzzing?

Fuzzing is an automated software testing technique that repeatedly executes a target using large numbers of generated inputs in an attempt to discover unexpected behaviour. Rather than manually constructing every possible Binder transaction, a fuzzer continuously creates new inputs, executes them, observes the result, and repeats the process thousands or even millions of times. If one particular input exposes an unexpected condition-such as a crash, memory corruption, failed assertion, or kernel warning-the input is saved for further investigation.

Instead of asking "Can I think of an input that breaks Binder?", fuzzing asks, "Can the computer generate millions of inputs faster than I ever could?"

Why Fuzz Binder?

Binder is one of Android's largest and most exposed kernel attack surfaces. Every application communicates with system services through the Binder driver, meaning an enormous variety of transaction layouts, object types, handles, file descriptors, and nested IPC interactions are processed every day. While the Binder driver enforces numerous validation checks, it must also process attacker-controlled data originating from unprivileged applications. This combination of complexity, reachability, and trusted execution makes Binder an excellent target for automated testing.

  • Large and complex parsing logic.
  • Numerous object types and transaction layouts.
  • Heavy use of locking, reference counting, and lifetime management.
  • Directly reachable from unprivileged applications.
  • Historically responsible for multiple kernel vulnerabilities.

Types of Fuzzing

Approach Description
Black-box Generates inputs without any knowledge of the program's internal behaviour. The fuzzer observes only whether execution succeeds, fails, or crashes.
White-box Uses information about the program itself, such as symbolic execution or constraint solving, to generate inputs capable of reaching difficult execution paths.
Grey-box Combines automated input generation with lightweight execution feedback, allowing the fuzzer to prioritize inputs that explore new portions of the program.

Why Coverage-Guided Fuzzing?

Modern kernel fuzzers are typically coverage-guided grey-box fuzzers. Instead of generating completely random inputs forever, they continuously measure which portions of the target have already been executed and then prioritize inputs that expand execution into previously unseen code. This allows the fuzzer to gradually explore increasingly complex execution paths instead of repeatedly exercising the same code.

Section 04a

How Coverage-Guided Binder Fuzzing Works

Coverage-guided fuzzing transforms the Binder driver from a black box into a measurable state space. By leveraging KCOV and structured syscall descriptions, we can systematically explore the deepest reaches of binder.c, mapping execution paths that would otherwise remain unreachable to random input.

1. The Necessity of Structure: Why Not Random Bytes?

The Binder driver, accessed via ioctl(BINDER_WRITE_READ), is strictly typed. It expects a specific union of commands (BC_TRANSACTION, BC_FREE_BUFFER, etc.) coupled with a complex hierarchy of binder_transaction_data objects.

If a fuzzer sends random bytes, the kernel's validation logic-specifically binder_transaction()-will fail during the initial copy-from-user or offset-array validation. Random fuzzing hits a "validation wall." Syzkaller bypasses this by using syzlang descriptions. These definitions map the exact ABI of Binder, allowing the fuzzer to generate valid binder_object layouts, correct handle types, and properly aligned offset arrays.

2. The Instrumentation Engine: How KCOV Works

KCOV provides the "eyes" for the fuzzer. When the kernel is compiled with CONFIG_KCOV=y, the compiler injects a callback at the entry of every basic block. During the execution of a Binder program, the executor maps a shared memory region where the kernel writes the address of every executed block.

3. Corpus Evolution and Mutation Strategy

The corpus is not just a pile of data; it is an evolutionary library.

  • Splice: Combining two successful transactions to create a complex chain.
  • Insert/Delete: Testing the driver's handling of missing or out-of-order commands.
  • Argument Mutation: Flipping flags like TF_ONE_WAY or modifying buffer_size to trigger allocation errors or boundary overflows.
A program is "retained" if, and only if, it covers a new edge in the Control Flow Graph (CFG) of binder.c. This ensures the fuzzer is constantly pushing deeper into error-handling paths and complex object translation routines.

4. Binder-Specific Evolution

Binder's complexity arises from its ability to handle nested transactions and object translation. When binder_translate_fd() is called, the driver modifies the caller's file descriptor table. The fuzzer evolves by:
1. Establishing a base transaction.
2. Adding nested objects that require reference counting.
3. Attempting to trigger binder_cleanup_transaction() while objects are in flight.
This creates "descendant" transactions-single initial triggers that cascade into thousands of interactions within the kernel.

5. Crash Discovery and Minimization

Once a crash occurs (detected by KASAN/UBSAN), Syzkaller triggers the minimization loop. It attempts to remove every single command from the crashing program one by one. If the crash persists, the command is removed permanently. This reduces a massive, thousand-line syscall log down to a 5-line C reproducer, enabling the high-fidelity root cause analysis required for CVE-level discoveries.

Practical Research Outcomes

While preparing the material and demonstrations for this webinar, a logical vulnerability was independently discovered within the new Rust Binder driver implementation (drivers/android/binder/allocation.rs). Although another researcher submitted an upstream patch for this exact flaw just two days prior to my planned disclosure, its technical root cause serves as an excellent case study for driver analysis.

Component / Function Status
rust_binder - Allocation::drop() Stride Mismatch Independently Discovered • Duplicate Disclosure

Technical Root Cause & Mechanics:

The flaw lives inside the Drop implementation for Allocation. When freeing an allocation, the driver iterates through an offsets array composed of 64-bit entries (binder_size_t) to clean up underlying binder objects. However, the loop was written using a step size of size_of::<usize>():

for i in offsets.step_by(size_of::<usize>()) { ... }

• On 64-bit Kernels: usize matches u64, making the calculation size_of::<u64>(). The loop increments by 8 bytes perfectly, causing zero harm.

• On 32-bit Kernels: usize drops to 4 bytes. This forces the loop to walk the 8-byte entries in narrow 4-byte steps. Instead of cleanly processing an $N$-entry array, the driver steps through it $2N$ times.

During these shifted iterations, cleanup_object() parses the upper 32 bits of the 64-bit entries. Since these high words are always zero, the driver interprets them as offset 0. It cleans up the object located at offset 0 an extra $N$ times, triggering a reference count over-decrement.

This corrupts Binder's structural reference accounting entirely, causing premature strong reference releases (BR_RELEASE). On 32-bit ARM systems, if the over-decrement drops the counter below zero, the driver's internal mitigation catches the underflow and forces a kernel panic: rust_binder: Failure: refcount underflow!.

The fix addresses this by strictly setting the iteration stride to size_of::<u64>() and explicitly narrowing the value via try_into() when performing the read.
