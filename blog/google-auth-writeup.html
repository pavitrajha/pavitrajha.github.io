1. Preface

Most vulnerability classes have names. Buffer overflows. SQL injection. SSRF. They describe what goes wrong at the implementation level — a developer wrote something incorrectly, memory was mishandled, input was unsanitized.

This is not that kind of vulnerability.

What I found in Google's infrastructure is better described as an authentication inheritance failure — a class of architectural mistake where a system exposes a specialized interface that is contractually required to inherit security controls from its parent authentication stack, but silently does not. The interface looks hardened from the outside. Internally, it is operating on a raw, unprotected API that was never designed for public exposure.

The result: an unauthenticated attacker with a wordlist and a proxy could enumerate valid email accounts belonging to law enforcement officials, then brute-force their passwords — against a system that processes emergency government data requests — at unlimited scale, with zero server-side resistance.

When I pulled the thread further, I found that the same architectural failure was not specific to one portal. It was a systemic property of how Google provisions every custom login interface across its entire Workspace ecosystem — affecting approximately fifteen million organizations globally.

Google accepted the report as P1 severity 1. They awarded $0. They called it an abuse risk. Then they called it "not a bug." After 386 days and 13 follow-up messages, I am publishing this.

2. Discovery — How LERS Caught My Eye

I was doing surface mapping across Google subdomains — methodical enumeration and manual inspection. I treat every component of a web interface as an independent state machine: not "what does this page do" but "what states can this component enter, and what happens at the boundaries between them."

One subdomain stopped me: lers.google.com — Google's Law Enforcement Request System. This is the platform used by verified law enforcement and government officials globally to submit legal data requests, track investigation-related subpoenas, and receive Google's responses to them.

Google LERS Documentation
"LERS is a system in which a verified law enforcement agent can securely submit a legal request for user data, view the status of the submitted request, and download the response submitted by Google."

The login page was visually unremarkable. Standard Google branding. But one thing was immediately unusual: the email input field was pre-filled — not with a placeholder, but with a hardcoded domain suffix seeded to accept input in the format [firstname]@lers.google.

My immediate question was not "what does the login do." It was: why does this page look different from every other Google login page? And specifically: what did they have to remove from the standard flow to make this prefilled UI work?

That question led directly to the vulnerability.

Methodology Note
The prefilled domain UI is a surface-level signal that something architecturally different is happening beneath it. When you customize a frontend to this degree, you're diverging from the standard flow — and every divergence is a potential security delta. The question is always: what controls did the standard flow have that this custom path removed?

3. Authentication Architecture — What Was Supposed to Happen

Google's consumer-facing authentication is handled through a system internally referred to as GlifWebSignIn. This is a layered authentication pipeline where the outermost layer handles all hardened security controls:

  • Rate limiting on authentication attempts
  • CAPTCHA enforcement after suspicious request volume
  • Account existence response normalization (preventing enumeration oracles)
  • Password attempt throttling
  • IP-based abuse detection

Beneath this hardened surface layer is a raw internal API — the batchexecute endpoint — that the frontend calls to perform actual credential verification. This API was designed for internal consumption. It was never meant to be callable directly by external clients without the security wrapper in front of it.

Normal Authentication Flow

STANDARD GOOGLE LOGIN (accounts.google.com) ────────────────────────────────────────────────── User ──► accounts.google.com │ ▼ GlifWebSignIn Layer (HARDENED) │ │ ✓ Rate limiting enforced │ ✓ CAPTCHA after threshold │ ✓ Enumeration protection │ ✓ IP-based abuse detection │ ✓ Response normalization │ ▼ batchexecute API (internal) │ ▼ Credential verified. Result returned.

LERS / Workspace Prefilled Login Flow

LERS / WORKSPACE TENANT LOGIN ────────────────────────────────────────────────── User ──► lers.google.com (prefilled UI) │ │ ✗ GlifWebSignIn layer STRIPPED to build custom UI │ ✗ Rate limiting: ABSENT │ ✗ CAPTCHA: ABSENT │ ✗ Enumeration protection: ABSENT │ ✗ Response normalization: ABSENT │ ▼ batchexecute API (raw, unprotected) │ ▼ Credential verified. Oracle leaked. No defense.

4. The LERS Oracle — Technical Breakdown

The Endpoint

Intercepting the login request from LERS reveals the underlying API call:

POST /v3/signin/_/AccountsSignInUi/data/batchexecute
    ?rpcids=MI613e
    &source-path=/v3/signin/identifier
    &f.sid=5908279343366079745
    &bl=boq_identityfrontendauthuiserver_20260201.08_p0
    &hl=en
    &_reqid=278278
    &rt=c
Host: lers.google.com
Protocol: HTTP/2

# Direct call to raw batchexecute RPC layer.
# No rate limiting layer in the request path.
# No CAPTCHA enforcement. No abuse detection.

Oracle 1 — Account Existence

The API returns HTTP 200 regardless of whether an account exists. The internal JSON response body differs in a consistently detectable way:

Account Does NOT Exist
HTTP/2 200 OK

[response body contains]

/v3/signin/rejected

→ Email address is invalid.
→ No such account registered.
Account EXISTS
HTTP/2 200 OK

[response body contains]

INITIALIZED

→ Email address is valid.
→ Account confirmed active.

This is a textbook account existence oracle — a binary signal leaked through response body content that allows an attacker to determine with certainty whether any given email address is registered, at zero authentication cost. Both responses return HTTP 200; the oracle is entirely in the body.

The Email Format

LERS uses a predictable email naming convention: firstname@lers.google (no .com suffix — confirmed during testing). The prefilled login UI seeds the domain portion automatically; only the first name is needed as input. 

# Burp Intruder configuration
Payload position: §firstname§@lers.google
Payload list:     names.txt (common first names)
Filter:           grep "INITIALIZED" → valid account confirmed

# Results from testing run
david@lers.google     → INITIALIZED           ← valid
sarah@lers.google     → INITIALIZED           ← valid
john@lers.google      → INITIALIZED           ← valid
xqzrt@lers.google     → /v3/signin/rejected   ← no such account

# Total valid accounts discovered in testing run: 88+

Oracle 2 — Password Validation

The same batchexecute endpoint — with a minor parameter modification — handles password verification and leaks a binary result through the same response body differentiation pattern. No rate limiting. No CAPTCHA. No lockout after N failed attempts. 

# Password spray against confirmed-valid account
Target:           sarah@lers.google   # confirmed INITIALIZED
Payload list:     rockyou.txt / common passwords
Endpoint:         same batchexecute, modified parameter set

# Zero server-side resistance observed:
# - No 429 Too Many Requests
# - No CAPTCHA challenge triggered
# - No account lockout after threshold
# - No delay injection
# - No IP block after sustained volume

No Throttling — Confirmed

Over 10,000 sequential requests were sent to the endpoint without receiving a single 429 Too Many Requests response. The server accepted every request without degradation, delay injection, or CAPTCHA challenge. A screenshot capturing 2,000+ requests with zero defensive responses was included in the original VRP report as evidence.

Critical Impact
An unauthenticated attacker could enumerate every valid LERS account and run password spraying attacks at full network speed with zero server-side resistance. No prior access. No insider knowledge. One wordlist. The only limit is the attacker's bandwidth.

5. Root Cause — The Architectural Finding

After confirming the LERS vulnerability, the question I kept returning to was: why did this happen? Not "what went wrong in this one endpoint" but "what is the systemic condition that made this mistake possible?"

When Google built the custom prefilled login experience for LERS, the entire GlifWebSignIn security control layer was removed from the request path. The UI was rebuilt to support the prefilled domain format, but the security inheritance from the standard flow was silently lost in the process. The interface was technically functional — authentication happened — but the controls were simply gone.

Vulnerability Class Defined
A specialized authentication interface that fails to inherit mandatory security controls from its parent authentication architecture. The interface is technically functional. The controls are simply absent. No memory was corrupted, no injection was performed, no filter was bypassed — the controls were never there. They were supposed to be inherited. They were not.

This failure mode is particularly dangerous because it is architecturally invisible. External audits see a working login. Security scanners see a 200 response. The functional behavior is correct. The security envelope is gone.

6. Scope Expansion — The Workspace Enrollment Oracle

Once I understood the root cause, a second question became obvious: is LERS the only place Google has built this kind of specialized prefilled login interface?

It was not.

Google exposes a documented URL pattern for all Workspace tenant organizations: 

https://mail.google.com/a/<company-domain>
https://drive.google.com/a/<company-domain>

# When a valid Workspace domain is placed in this URL:
# → user is redirected to a custom prefilled login interface
# → structurally identical to LERS
# → calls the same raw batchexecute API
# → hardened control layer: ABSENT

The Workspace Enrollment Oracle

The initial redirect behavior itself leaks an oracle — revealing whether any given domain is an active Google Workspace client:

This means the entire Google Workspace client population can be mapped by iterating known domains through this URL pattern. Any domain that does not return the error message is confirmed as an active Workspace client with a vulnerable prefilled login interface exposed.

7. Real-World Threat Context — The Tamagami Precedent

In 2024, threat actor groups operating under the designation Tamagami used infostealer malware to compromise approximately 45 law enforcement accounts with access to Google's LERS platform. These accounts were monetized — sold as a service to submit fraudulent Emergency Data Requests (EDRs) and obtain user data from Google under false legal pretense. (Under The Breach, 2024)

Prerequisites Targeted malware deployment, endpoint compromise, credential theft infrastructure None. Wordlist + HTTP proxy.
Operational Complexity High — requires active C2, opsec, targeted phishing campaigns Near zero. Burp Intruder with a names list.
Accounts Obtained ~45 law enforcement accounts Unlimited — bounded only by attacker bandwidth
Forensic Footprint Malware artifacts, C2 traffic, endpoint telemetry Zero server-side logging of abuse (no 429s fired)
Outcome Google responded to fraudulent EDRs Same outcome achievable by commodity attacker at arbitrary scale
Context
The Tamagami operation — which resulted in Google responding to fraudulent government data requests — was operationally complex and yielded 45 accounts. This vulnerability makes the same outcome achievable by any attacker with commodity tooling, at arbitrary scale, with no forensic trail.

9. Remediation

The correct fix is architecturally straightforward, though it requires consistent enforcement across every specialized login interface in Google's infrastructure:

①
Mandatory GlifWebSignIn layer enforcement
All prefilled or tenant-specific login interfaces must route through the full hardened GlifWebSignIn control layer. Security control inheritance must be enforced at the architectural layer, not optionally applied per-implementation.
②
batchexecute endpoint hardening
The batchexecute authentication RPC endpoint must not be reachable without rate limiting, CAPTCHA enforcement, and enumeration protection regardless of which frontend interface invokes it. Defense-in-depth at the API layer, not just the frontend layer.
③
Account existence response normalization
The INITIALIZED / /v3/signin/rejected binary oracle must be eliminated or equalized. Account existence must not be inferrable from response body content differences.
④
Workspace enrollment oracle removal
The /a/<domain> redirect behavior must not differentiate between Workspace clients and non-clients in a way that leaks tenant membership. The error message "domain isn't using Google Workspace" is itself a data disclosure oracle.

Fix Status: Partial remediation was applied to the LERS portal at some point during the 386-day disclosure period. The systemic Workspace-wide architectural condition was not confirmed as fixed as of the disclosure date of this writeup.

10. Conclusion

The most dangerous architectural vulnerabilities are not the ones where something was implemented incorrectly. They are the ones where a security control was supposed to be inherited and was not — where a system looks correct from the outside because its parent is correct, but internally is operating with none of the parent's protections.

Google's GlifWebSignIn is a hardened authentication pipeline. The LERS portal and every Google Workspace tenant login interface were supposed to be extensions of it. They were not. They were parallel implementations that called the same internal API directly, with the entire security envelope stripped away.

The result was an unauthenticated, unlimited-scale enumeration and credential spraying surface against law enforcement infrastructure and fifteen million organizations simultaneously — accessible to any attacker with commodity tooling and a name list.

I reported this on June 6, 2025. I was told "nice catch." I maintained coordinated disclosure for 386 days. I withdrew a Black Hat submission to give more time for a fix. I filed full scope expansion reports. I documented real-world APT precedent. I sent 13 follow-up messages.

Google awarded $0 and called it "not a bug."

I am publishing this because the public has a right to understand when infrastructure they depend on — law enforcement data systems, enterprise authentication for 15 million organizations — has been vulnerable at this scale. And because 386 days of silence from a billion-dollar security program is not responsible disclosure. It is suppression by bureaucratic attrition.
