Linux libceph: Unsafe Bare Decode in decode_watchers()

Linux Kernel libceph Client | net/ceph/osd_client.c | Slab Memory Safety | Vulnerability Write-up

1. Summary

An out-of-bounds read vulnerability existed in the Linux kernel's libceph client within decode_watchers() in net/ceph/osd_client.c. The function used a bare ceph_decode_32() operation immediately after ceph_start_decoding(), without verifying that four bytes remained in the receive buffer.

The root cause is that ceph_start_decoding() validates that struct_len bytes remain after the encoding header, but accepts struct_len=0 as valid. Internally, ceph_decode_need(p, end, 0, bad) succeeds for a zero-byte requirement. As a result, a malformed reply can successfully complete the initial decoding step with p == end, leaving zero bytes available for the next field.

The immediately following bare ceph_decode_32(p) then reads four bytes past the validated boundary. The value obtained from out-of-bounds memory is assigned directly to *num_watchers and passed to kzalloc_objs() as the watcher allocation count.

2. Vulnerability Execution Path

The vulnerable parser handles watcher-list replies received from a Ceph OSD: 

net/ceph/osd_client.c
  |
  v
Kernel Ceph client processes a reply for CEPH_OSD_OP_LIST_WATCHERS
  |
  v
decode_watchers()
  |
  +-- ceph_start_decoding()
  |     |
  |     +-- struct_len=0 is accepted
  |     |
  |     +-- returns successfully with p == end
  |
  v
*num_watchers = ceph_decode_32(p)
  |
  +-- No bounds check
  |
  +-- Reads 4 bytes past end when p == end
  |
  v
kzalloc_objs(**watchers, *num_watchers, GFP_NOIO)
```

The vulnerable condition occurs when a malicious or compromised OSD sends an obj_list_watch_response_t reply whose encoded structure has struct_len=0. The header parser accepts the empty structure, but the parser then immediately expects to read the four-byte watcher count.

At that point, the decoding cursor is already positioned exactly at the end of the validated buffer. The bare decode crosses the boundary before any subsequent validation can occur.

```

3. Vulnerability Description & Mechanics

```

The vulnerable sequence is straightforward:

``` 
ceph_start_decoding(p, end, 1, "obj_list_watch_response_t",
                    &struct_v, &struct_len);

*num_watchers = ceph_decode_32(p);
```

ceph_start_decoding() establishes that the encoded structure header itself is valid and that the declared structure length fits within the remaining buffer. However, a declared length of zero satisfies that validation.

``` 
struct_len = 0

ceph_decode_need(p, end, 0, bad)
    |
    +-- zero bytes are required
    |
    +-- validation succeeds
    |
    v
ceph_start_decoding() returns success

p == end
```

The parser has therefore successfully validated an empty structure, but decode_watchers() still proceeds to decode a mandatory four-byte watcher count.

``` 
*num_watchers = ceph_decode_32(p);
```

Because the bare decoder advances and reads without checking end, this becomes a four-byte out-of-bounds read when p == end.

The resulting value is not merely discarded. It becomes the watcher count passed directly into:

``` 
*watchers = kzalloc_objs(**watchers, *num_watchers, GFP_NOIO);
```

Consequently, memory located beyond the validated receive buffer can influence the allocation-count decision taken by the parser.

```

4. Source Code Analysis

```

The vulnerable code in decode_watchers() was:

``` 
if (ret)
        return ret;

*num_watchers = ceph_decode_32(p);

*watchers = kzalloc_objs(**watchers, *num_watchers, GFP_NOIO);
if (!*watchers)
        return -ENOMEM;
```

There is no bounds validation between the successful return from ceph_start_decoding() and the four-byte decode.

This is particularly notable because the sibling parser decode_watcher() already follows the defensive decoding pattern:

``` 
ceph_decode_copy_safe(p, end, ...);
ceph_decode_64_safe(p, end, ...);
ceph_decode_skip_32(p, end, ...);
```

Those helpers explicitly verify that sufficient bytes remain before advancing the parser cursor. decode_watchers() was the inconsistent site that retained a bare decoder for the watcher count.

Safe decoding pattern

The fix changes the operation to the existing bounds-checked variant:

``` 
ceph_decode_32_safe(p, end, *num_watchers, bad);
```

The safe decoder verifies that four bytes remain between p and end. If the malformed reply leaves p == end, decoding fails immediately rather than reading beyond the receive buffer.

```

Anatomy of the read

The allocated buffer occupied the six-byte range:

``` 
[ffff8880085936c8, ffff8880085936ce)
```

The decoding cursor was positioned at 0xffff8880085936ce, exactly one byte beyond the valid range. The bare decoder then attempted a four-byte read starting from that address.

KASAN identified the operation as a slab out-of-bounds read and reported that the access occurred immediately to the right of the six-byte allocation.

6. Why 0xCCCCCCCC Matters

```

The observed watcher count was:

``` 
num_watchers = 3435973836
             = 0xCCCCCCCC
```

This value corresponds to KASAN poison/redzone memory in the test environment rather than valid protocol data. Its appearance demonstrates that the decode operation crossed the boundary of the allocated object and consumed memory beyond the six-byte receive buffer.

In this reproduction, the value is therefore useful as direct evidence of the invalid memory access. The important security property is the bounds violation itself: a malformed encoded structure was accepted by the header parser, after which the next mandatory field was decoded without independently verifying that its bytes remained available.

```

7. Threat Model & Impact Assessment

```
  • Primary Primitive: A four-byte slab out-of-bounds read beyond the validated Ceph reply buffer.
  • Data Flow: The value obtained from out-of-bounds memory is assigned to *num_watchers and passed into kzalloc_objs() as the watcher allocation count.
  • Attack Vector: A malicious or compromised OSD sends a malformed obj_list_watch_response_t reply with struct_len=0.
  • Reachable Operation: The affected parser processes replies associated with CEPH_OSD_OP_LIST_WATCHERS.
  • Required Position: The attacker must be able to provide the relevant OSD response to the kernel Ceph client.
  • Privilege Requirement: Under the stated threat model, no additional local privilege is required after the attacker can act as, control, or compromise the responding OSD.

The demonstrated bug is a memory-safety violation resulting in an out-of-bounds read. The KASAN reproduction confirms the read primitive and the propagation of the resulting value into the watcher-count allocation path.

The exact consequences beyond the demonstrated out-of-bounds read can depend on allocator state, surrounding memory, protocol handling, and the caller context. Therefore, this write-up does not claim exploitation capabilities beyond those directly demonstrated by the supplied reproduction.

```

8. Remediation

```

The upstream fix replaces the bare decoder with the existing bounds-checked helper and adds a malformed-message error path:

``` 
diff --git a/net/ceph/osd_client.c b/net/ceph/osd_client.c
index 2ff00070c..2cdac81a6 100644
--- a/net/ceph/osd_client.c
+++ b/net/ceph/osd_client.c
@@ -5030,7 +5030,7 @@ static int decode_watchers(void **p, void *end,
        if (ret)
                return ret;

-       *num_watchers = ceph_decode_32(p);
+       ceph_decode_32_safe(p, end, *num_watchers, bad);
        *watchers = kzalloc_objs(**watchers, *num_watchers, GFP_NOIO);
        if (!*watchers)
                return -ENOMEM;
@@ -5044,6 +5044,8 @@ static int decode_watchers(void **p, void *end,
        }

        return 0;
+bad:
+
+       return -EINVAL;
 }
```

The safe variant receives both the current cursor and the buffer boundary:

``` 
ceph_decode_32_safe(p, end, *num_watchers, bad);
```

Before reading the four-byte value, it verifies that sufficient bytes remain. A malformed reply that leaves p == end therefore takes the bad path and returns -EINVAL instead of accessing memory outside the validated message.

```

9. Why the Fix Is Correct

```

The fix does not alter the protocol layout or introduce new parsing semantics. It enforces the same invariant already used throughout adjacent Ceph decoding code: every variable-length or fixed-width field must verify that the required bytes remain before it is consumed.

The sibling decode_watcher() implementation already demonstrates this approach through safe decoding helpers. Applying the same pattern to the watcher-count field closes the gap created by relying solely on the earlier structure-header validation.

This distinction is important:

``` 
ceph_start_decoding()
    validates the encoded structure header and declared length

ceph_decode_32_safe()
    validates the availability of the next four-byte field
```

Successful validation of the first property does not guarantee the second when the declared structure length is zero.

```

10. Affected Configurations

```
  • Vulnerable Component: Linux kernel libceph client.
  • Source File: net/ceph/osd_client.c.
  • Vulnerable Function: decode_watchers().
  • Reachable Protocol Path: Processing an OSD response for CEPH_OSD_OP_LIST_WATCHERS.
  • Configuration Requirement: A kernel client using Ceph client functionality and communicating with an OSD capable of supplying the malformed response.
  • Threat Model: A malicious or compromised OSD, including an OSD operating in an environment where the kernel client does not fully trust every responding storage peer.
```

11. Upstream Patch & Timeline

The vulnerability was fixed upstream in net/ceph/osd_client.c by replacing the unsafe bare watcher-count decode with ceph_decode_32_safe().

The patch identifies commit a4ed38d7a180 ("libceph: support for CEPH_OSD_OP_LIST_WATCHERS") as the introducing commit and includes Cc: stable@vger.kernel.org for stable-tree consideration.

The final revision incorporated review feedback from Viacheslav Dubeyko. Version 3 renamed the error label from e_inval to bad. Version 2 corrected the commit message and retracted earlier overstated impact claims after verification with a follow-up KASAN harness.

12. Key Takeaway

This vulnerability illustrates a subtle but important parser invariant: successful validation of an encoded structure header does not automatically validate every field subsequently decoded from that structure.

A zero-length structure can legitimately satisfy a length check while leaving the parser cursor positioned exactly at the end of the buffer. Any subsequent bare decode then becomes unsafe unless it independently establishes that its required bytes remain. 

struct_len = 0
      |
      v
ceph_start_decoding() succeeds
      |
      v
p == end
      |
      v
bare ceph_decode_32()
      |
      X
      |
4-byte out-of-bounds read

Replacing the bare decode with ceph_decode_32_safe() restores that missing invariant and causes malformed replies to be rejected before memory outside the validated message boundary is accessed.
