Linux libceph: Three Unchecked Decodes in the Ceph Kernel Client

Linux Kernel libceph Client | net/ceph/ | Slab Memory Safety | Research Overview

1. Summary

Three out-of-bounds read vulnerabilities were found in the Linux kernel's libceph client, in the code that parses replies from Ceph OSDs. They are tracked as CVE-2026-68082, CVE-2026-80557 and CVE-2026-80561. All three are fixed upstream. Each has its own technical write-up, linked below.

The three bugs share one root cause. ceph_start_decoding() accepts struct_len=0 as valid, which can leave the decode cursor at p == end. Code that then reads a fixed-width field without its own bounds check reads past the end of the receive buffer. Each of the three bugs is a different site where this happened.

2. The Common Pattern

ceph_start_decoding()
  - struct_len = 0 passes validation
  - p == end on return
      |
      v
bare ceph_decode_*() / raw *p += n
  - no check that the bytes remain
      |
      v
read (or cursor advance) past the validated buffer

Neighbouring parsers in the same files already used the bounds-checked _safe helpers. The fixes bring the remaining sites in line with that pattern, so the invariant is now consistent: every read and every cursor advance verifies that the bytes remain inside the received message.

3. The Three Findings

CVE Function / file Issue Fix commit CVSS Write-up
CVE-2026-68082 decode_lockers()
cls_lock_client.c		 Two bare decodes (lock count, lock type) after a zero-length struct 9.8 (kernel.org CNA) OOB 1
CVE-2026-80557 decode_watchers()
osd_client.c		 Bare 4-byte decode of the watcher count, fed into an allocation size 9.8 (kernel.org CNA) OOB 2
CVE-2026-80561 decode_locker()
cls_lock_client.c		 Unchecked name copy, unchecked timespec skip, unchecked length decode plus skip 9.8 (kernel.org CNA) OOB 3

The KASAN-confirmed primitive in each case is a slab out-of-bounds read of up to 4 bytes (CVE-2026-68082, CVE-2026-80557) or a 4-byte read plus unchecked cursor movement (CVE-2026-80561). The write-ups state exactly what was demonstrated.

4. Attacker Model

  • Position required: the attacker must be able to send replies to a kernel Ceph client as an OSD, either a malicious OSD or a compromised one. A network attacker who can inject into an unprotected OSD session is a second route.
  • Privilege required: none beyond that established OSD session.
  • Reachable operations: lock.get_info (including RBD exclusive lock acquisition) and CEPH_OSD_OP_LIST_WATCHERS.
  • Not affected: Ceph server daemons. This is the in-kernel client only.

5. Where the Kernel Client Is Used

The vulnerable code is the kernel client used to mount Ceph block (RBD) and file (CephFS) storage on a host. It is not used by Ceph's own storage daemons.

  • Kubernetes with Rook and ceph-csi: the CSI driver can attach RBD volumes through the kernel module (krbd) and mount CephFS volumes through the in-kernel driver.
  • Proxmox VE: uses krbd for RBD storage.
  • Any host running rbd map or mount -t ceph.

For scale, two published survey figures give context. They measure adoption of the platforms, not the number of vulnerable kernel clients, and should not be multiplied together:

  • CNCF Annual Cloud Native Survey 2025 (published January 2026): 82% of container users run Kubernetes in production.
  • CNCF Annual Survey 2022: Rook was in production at 10.4% of respondents.

Both are self-selected survey results. Exposure here means potentially exposed deployments, not confirmed affected systems.

6. Remediation

Run a kernel that contains the fixes. Stable backports for CVE-2026-68082 are present in the 5.10.y, 5.15.y, 6.1.y, 6.6.y, 6.12.y and 6.18.y trees, in addition to 7.1.y and mainline. Check each write-up for the fix commit, and check your distribution's kernel changelog for the corresponding backport. Where an update is not yet possible, restrict which hosts can act as OSDs for your clients and use authenticated, protected sessions.
